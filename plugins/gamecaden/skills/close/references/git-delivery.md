# Git 交付与收尾

本次涉及 Git 交付时使用；允许范围与策略来源见[项目 Git 策略](../../../shared/git-policy.md)。未采用的推荐项不构成操作授权。

## 1. 核对本次终点与实际现场

从原 Task、用户指示和已采用策略确定需要交到哪里：本地文件、指定分支提交、PR、目标分支集成、远端同步，或明确发布。它们各自有结果，不是 Task 的新状态枚举。

核对仓库/工作树、分支、相关差异、已有暂存内容、目标和远端。保护无关修改与永久工作树；按已定位的实际来源操作，不根据目录名或默认分支名猜测。

## 2. 提交本次拥有的内容

按实际需要组织提交，不要求一个 Task 恰好一个提交，也不要求每个步骤提交。develop 已形成的有效检查点直接保留，close 补齐剩余内容。

确认拟提交集合中的代码、场景、必要资产/元数据和记录确属本次；生成物、大文件和原始素材服从项目存储/忽略规则。只暂存任务拥有的差异；其他人的暂存项或同文件混合修改不能直接一并提交，无法查明归属时只澄清该部分。

提交后核对实际包含的内容与可追溯依据。没有本次待提交变化时不制造空提交，已有提交足以承担交付就直接使用。

## 3. 集成、推送与关联动作

| 动作 | 本次何时需要与如何核对 |
|---|---|
| 集成/合并 | 要求进入约定目标分支时执行；核对目标实际包含结果及必要集成检查 |
| PR | 按项目已采用的评审路线创建/更新并满足相应条件，遵守宿主附件/关联要求；PR 已创建不证明已合并 |
| Push | 需要且已授权同步时执行，核对正确远端、分支和实际结果；任务分支已推送不证明目标分支已集成 |
| Tag/Release/部署 | 仅在相应目标或发布策略明确要求时执行，使用对应验证与授权 |
| 清理分支/工作树 | 清理已经获准、成果和必要证据安全保留且无未移交变化或活跃使用时执行 |

目标已变化、合并或冲突修复改变实现时，核对新基线并补相关验证；其他仍有效证据保留。单纯记录提交产生新 SHA 不要求重跑无变化的游戏检查。

可以按既定语义解决的普通冲突在已有集成授权内处理；涉及实质产品取舍、覆盖他人结果或不清楚的历史处理时，先准备具体差异与影响，再解决缺少的决定。自动交付不自动授权强推、覆盖他人提交或重写共享历史，也不绕过保护条件。

核对成果时考虑实际集成方式与内容映射，不能只看分支名称、PR 标题或旧跟踪状态。已知推送会触发的外部效果按策略约定处理，发生新的未覆盖影响时先处理相关范围。

## 4. 把结案写回真实权威位置

保存被测基线的事实与剩余 Git 动作，按本次目标完成提交、集成、必要检查及同步。只有目标分支/远端确实取得结果时，才将相应 Spec 与结论写成该基线已经采用；候选通过先按候选范围表述。

集成后核对结案记录应由哪个实际分支/工作树维护，避免只更新即将清理的旧工作树。原 Task 保留身份与明确来源；不要另建同目标任务记录来代替合并或同步。

必要 Git 交付与权威回写共同决定本次收尾是否完成。结案记录自身需要版本控制/远端同步时，按同一已采用策略补齐相应记录提交与同步；不要留作未说明的脏修改。

关联已有实现提交、目标引用、PR 或原生回执即可，不要求记录包含承载它自己的提交 SHA，避免为更新自身 SHA 不断追加提交。最终结果回读核对，不为每条 Git 命令再写一份平行日志。

Git 动作与文件写回不构成天然跨系统事务。先写了 closed 但本任务必要交付/同步尚未完成时，按[关闭与同步](closure-and-sync.md)纠正不一致记录并保留可恢复下一步；状态字段不能证明完整交付。

## 5. 部分失败与恢复

提交、集成、推送、发布分别说明实际完成与未完成部分。推送失败但本地提交和验证成立时保留它们，继续处理远端欠项；不回滚已完成实现或用强推绕过拒绝。

连接中断导致远端结果不明时，先查询实际结果，再决定是否重试。原授权内可以安全重试的动作不必重复确认；分叉、冲突或保护检查未满足时，处理具体原因。

原目标仅为指定分支提交且已经满足时，可以按该范围关闭。原目标要求目标分支集成或远端交付时，这些欠项不能只标作后续而宣称完成。用户明确改变本次范围时，记录变化并按新条件处理。
